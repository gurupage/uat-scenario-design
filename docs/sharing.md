# 共有と利用環境の準備

公開するものは汎用Skill、補助コード、利用手順、空のひな形、架空の検証データです。案件原資料、完成シナリオ、資料マッピング、生成・評価結果、チーム固有の適用ルールは非公開で管理します。匿名の案件IDに置き換えただけでは、本文や組合せから固有情報が残る場合があります。

## 公開前の確認

- READMEからリンクされる文書と、公開予定の全ファイルを確認します。氏名、アカウント名、PC固有パス、社内URL、実案件名、実データ、個人的背景、作業ログを含めません。本文・表・依頼例・サンプルの注記を文脈ごと確認し、特定の利用者の案件数、進捗、導入予定が一般的な説明に紛れていないかを点検します。
- Gitを使う場合は、追加する差分とファイル一覧を確認します。過去にコミットした内容は、削除や.gitignore追加だけでは履歴から消えません。実案件を含む履歴がある場合は、その履歴を公開しない方法で共有物を作り直します。
- ZIPにする場合は下記の公開対象だけを選びます。プロジェクトフォルダ全体をそのまま圧縮すると、Gitの除外設定にかかわらずprivate/などが含まれます。
- 公開用コピーでnpm ci、npm run typecheck、npm testを実行し、非公開資料や過去の作業フォルダなしで動くことを確認します。

公開対象：

~~~text
README.md
DEVELOPMENT.md
プロセス設計.md
.gitignore
package.json
package-lock.json
tsconfig.json
skills/
scripts/          （.tsファイルのみ）
docs/
templates/        （記入前のひな形のみ）
inputs/           （管理方法を説明する.mdのみ）
evals/検証手順.md
evals/fixtures/   （架空資料のみ）
evals/samples/    （架空出力のみ）
~~~

この一覧は現在の構成に対するものです。追加したファイルを自動で公開可とは扱いません。node_modules、キャッシュ、private、runs、実験記録、旧版の保存フォルダは含めません。

### ファイルを残す基準

- 通常利用だけを配布する場合は、`skills/uat-scenario-design/`全体を使います。参照文書、package.json、検査・表示コードを一緒に含めます。
- 開発・更新も行うプロジェクトには、検証コード、架空データ、package-lock.jsonを含めます。旧形式の架空出力も、現在のテストが互換性確認に使うものは必要です。旧版プロジェクトの保存物とは区別します。
- `inputs/`と`templates/`は説明・未記入のひな形だけです。記入済みの資料一覧や案件マッピングを追加しません。
- ZIPは展開後の一覧と内容も確認します。Gitの除外設定だけで公開対象を決めません。

## 利用環境の準備

1. 公開用プロジェクトを取得・展開し、READMEの環境準備と検査を実行します。
2. 案件資料とマッピングは、所属組織で認められた非公開の方法で別途移します。
3. 非公開側のマッピングにあるパスを、利用環境の保存先に合わせます。評価用完成シナリオは生成担当が参照しない場所に分離します。
4. Skill更新時はREADMEの「1」、通常利用時は「2」の依頼例で開始します。採用済みの適用ルールがある場合は、版と対象範囲も指定します。

公開プロジェクトだけでは、非公開の案件資料や適用ルールは復元されません。評価記録や適用ルールを共有する場合も、公開用ファイルと分けて管理してください。
